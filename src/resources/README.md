- Android status bars have been removed from all screens.
- fonts/CormorantGaramond-Bold.ttf: static bold title font (variable font also retained), distributed under the adjacent OFL.

Resources are loaded from /resources/ on the classpath. IntelliJ currently marks
src as the source root, so keep resources inside src and retain this layout in
the compiled output/JAR. Do not mark src/resources as a separate resource root
without also updating the resource paths.

Without a server the login button lets everyone straight in, on demo data. With one,
it asks the host to sign the person in (HostBridge.signIn): the desktop asks for a name
and signs in by it, which the server allows while it has no Kakao key. In the browser the
web page signs people in (Kakao, or by name) before it starts this UI, hands over the
name (-Darchivefever.user) and the UI opens on that person's shelf; its own login screen
is not shown. AppShell.signedIn is the one place both ways arrive at. Logout tells the
host to end the session (HostBridge.signOut); in the browser that reloads the page into
its sign-in screen. The profile popup shows the name of whoever is signed in.

## Reading layouts

Figma nodes 294:1628 (412 x 917) and 328:2068 (1280 x 900).
ReadingPanel scales the complete scene uniformly and omits the Android status bar.
Stationery x/y are the top-left of the rotated Figma bounding box; width/height
are the unrotated content size. Do not rotate around x + contentWidth / 2.
Pencil and lens exports contain 28 logical pixels of shadow overflow; the
highlighter has its original Figma image-fill crop. Transparent stationery
areas pass mouse events through to the illustrations behind them.
Return uses the original ribbon atlas, and the paragraph uses bundled MaruBuri
with 14px line boxes (underlined only in the wide layout). Book title remains
the currently selected book; author/body text are still prototype content.
Resizing snaps between layouts without recentering the window. Return restores
the original main window size and location.

Reading snaps animate for 300ms with smooth acceleration/deceleration. Window
size interpolates without moving its origin, while 2x scene snapshots fade
between the portrait and open-book layouts. Input is suspended during the
transition and restored afterward. Resize events generated by the animation
are excluded from snap detection to avoid recursive transitions.

## Interactive reading tools

Choose pencil/highlighter/pen, then click a sentence. Underlines and highlights
are independent toggles; clicking the same sentence again removes that mark. Pen adds a
memo section beneath the paragraph for that sentence. Enter saves, Shift+Enter
inserts a newline, Escape leaves the draft unsaved. Clicking a saved memo edits
it again. Right-click a memo for Edit/Delete; saving an empty memo deletes it.
Magnifier cycles body and memo text through 18px / 11px / 14px body sizes;
book title and author remain fixed, without changing the annotations.

ReadingDocument stores annotations by sentence. Without a server they go to files
written atomically under ~/.archivefever/notes (override archivefever.notes.dir
for tests), one per book ID. With a server the document is given its marks and a
ReadingDocument.MarkStore: every underline, highlight and memo is then a request to
the server and counts only once the server has taken it; the file is not used.
Draft memo text stays in memory until Enter.

Pressing the tool in hand puts it down again. With no tool in hand, a press on a
sentence is for the passage it belongs to (ReadingText.setSentenceAction): the host
lets the reader correct its text and page or delete it (HostBridge.editPassage), and
the page is then read again from the server. In the browser the form for that is the
page's own HTML, because an HTML text box gets the phone's keyboard; on the desktop
it is a dialog.

ReadingToolsSmokeTest verifies sentence hit-testing, combined annotations,
Enter save, persistent reload, book isolation, magnifier cycle, scaled clicks,
and preservation across animated layout transitions.

Reading stationery lifts 6 logical pixels only while the pointer hovers over it.
Selection does not change brightness or keep the tool raised. The portrait reading screen no longer paints the tinted wall
layer; wallpaper trim, wood and page assets remain.

## Friends, book swaps and notifications

The friend and Book swap screens and the notification paper get their data through
archivefever.social.Social. Without a server that is DemoSocial (in-memory demo
people and swaps); with one, Backend connects ServerSocial, which calls the REST
API (see backend/README.md). AppShell.connectSocial switches the screens over.

- People are shown as name and "@handle". A name may be Korean (a Kakao nickname):
  the typewriter and heading faces have no Korean letters, so such text is drawn
  in the body face (SocialPanel.korean), and long names are shrunk to fit.
- "swap" on a friend shows only the books both have; a swap that was asked for
  sits in the Book swap cabinet as "waiting for @friend" until the friend accepts,
  and only then opens. In demo data DemoSocial.approveSwapForDemo stands in for
  the friend accepting, as approveRequestForDemo does for friend requests.
- Removing a friend ends the swaps being read with them, and keeps their records:
  such a swap stays in the cabinet as "once with @friend" and opens on the record
  as it stood, to read only. No tool marks anything there and the page says
  why (ReadingDocument.closed, from MarkStore.closed). A swap that was still
  waiting is simply gone.
- An accepted swap opens on the reading page with both readers' collected passages
  as one text, each under a line with its page and collector ("p.12 · @handle").
  The friend's memos are listed under the text; the user's own underlines,
  highlights and memos are the document's marks, kept on the server through
  ReadingDocument.MarkStore: making or removing one is a request, and when it fails
  the mark counts as not made. PassagePage lays the passages out and finds the
  passage, and the sentence within it, that a sentence of the page is.

MenuFlowSmokeTest covers menu hit areas, exact hover height, modal interception,
confirmation state, dismissal, logout/login and interactions at 65% scale.

wallpaper and camera shell are in images/addbook. The camera display is blank:
no camera device, sample book photo, capture code or recognition API is used.
Scan plays sounds/camera-shutter-click-07.wav asynchronously and opens the

released at the end of playback. Sound-device failure does not block the UI.

"or search by title", under the heading, opens BookSearchPanel in the camera
screen's place: the way to add a book whose barcode is not to hand. Words of a
title or an author are looked up when Enter or the magnifier is pressed (not while

and pressing one opens the same confirmation paper with the book's cover; yes puts
it on the shelf. Books already on the shelf are listed with ADDED and cannot be
picked. The screen names YES24 with a link, as its terms ask. "scan." has not moved.

A shelf book's "what's next?" paper has "remove from shelf" under read and scan.
It asks first, saying that the passages collected from the book and the marks on
them go too; a book being read with a friend stays, and the shelf says why.

The API result panel stays empty. No/Escape/outside click dismisses the review
for another scan. Yes remains disabled until a backend result is supplied;
no fake book is inserted. The alternate review header is visual text from the
Figma mockup and is not connected to a user-profile API. Backend result and
confirmation hooks are isolated in ScanConfirmationPopup for later integration.

ScaledAppView keeps the original mouse-click target when release opens a modal,

## Live camera on the phone

When the UI runs inside the phone app (see backend/README.md and mobile/README.md), the
app draws its live camera picture over the blank display of the camera illustration,
on both camera screens. CameraScanPanel.DISPLAY is that opening in design coordinates;
change it together with the camera artwork.

AppShell tells the host when a camera screen comes into view or is left, and when its
scan button is pressed (HostBridge.showCamera / hideCamera / capturePhoto), so the photo
is taken at the press. On Add book the photo is then uploaded to the server's scan and the
confirmation popup shows the book.

On Archive sentence the scan button asks the host for a page photo (HostBridge.capturePage).
The phone app reads the text on it, on the phone, and lets the reader pick lines on the
picture. The same button, now "save.", asks the host to save them (HostBridge.savePassage):
the app shows the picked text and the page number it found for correction, sends them to
the server, and answers with a PassageResult. Once saved, AppShell opens the book's reading
page. Back (Escape) on a captured page returns to the camera for another photo.

Connected to the server, the reading page of a shelf book shows the passages collected
from it in page order, a paragraph each, with a "p.127" line wherever the page changes
(LibraryController.page). ReadingDocument ends a sentence at every line break, so each
passage and page note is marked on its own. Marks are kept on the server by passage and
by sentence within the passage, so they stay with their passage when others are collected,
corrected or deleted. Marks made while they were still kept in a file on the device are
handed over to the server the first time the book is read, and the file is then removed.
ReadingText scrolls by drag or wheel once the text is longer than the page.

On the desktop there is no camera: without a server both screens behave as described
above, and with one (-Darchivefever.api) save opens a dialog to type the passage in.
